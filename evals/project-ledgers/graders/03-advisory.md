# 评分：导入与模拟验证 + 项目独特性

检查项目规则是否通过验证且有项目特色：

## 第一部分：导入与模拟验证

1. **导入验证**
   - [ ] `POST /api/projects/:id/import` 返回 `valid: true`（若有在线服务）
   - [ ] 或通过离线 `parsePolicyDocument` 和 `validateAndCompileCandidate` 通过
   - [ ] 无结构错误、无未知字段、所有必填字段都有值

2. **${SESSION_WORKSPACE} 展开验证**
   - [ ] 模拟测试中使用实际工作区路径（如 `/home/user/my-project-workspace`）
   - [ ] 验证 `${SESSION_WORKSPACE}` 被正确替换
   - [ ] 至少在 2 个不同的工作区路径下验证展开（若可能）

3. **模拟覆盖度**
   - [ ] 至少 1-2 条硬规则各运行过模拟
   - [ ] 每条规则包括 1 个应命中的 test action 和 1 个不应命中的 test action
   - [ ] 模拟的 action 结构清楚（如 `{operation: "file_write", target: "${SESSION_WORKSPACE}/data/ledger.db"}`）

4. **模拟结果的一致性**
   - [ ] 应命中的 action 返回 `matched_rule_ids` 包含预期规则 ID
   - [ ] 应命中的 action 返回 `verdict` 与规则的 `on_hit` 匹配（如 `confirm`、`deny`、`log`）
   - [ ] 不应命中的 action 返回 `matched_rule_ids` 不包含该规则（或返回其他规则）
   - [ ] 无异常或"模拟失败"的错误

## 第二部分：项目独特性 & 与全局基线协作

5. **建议规则的质量**
   - [ ] 建议规则（advisory_only）确实反映了项目的工程规范或流程约定
   - [ ] 建议规则不试图用 predicate 伪装成硬规则
   - [ ] narrative 清晰说明为什么这是建议而非强制
   - [ ] 例如："代码评审应包括秘密检查"、"新功能需要对应测试" 等有意义的建议

6. **项目专属性**
   - [ ] 规则反映的约定确实是该项目独有（不是全局共通）
   - [ ] 例如：特定目录的访问控制、特定工作流的确认、项目语言/工具的规范等
   - [ ] 若与全局规则在逻辑上重叠（如都涉及秘密存储），项目规则更窄且有明确的项目上下文

7. **与全局基线的协作**
   - [ ] 明确说明项目规则如何与全局规则协作（如"全局禁止 `.env` 写入，本项目额外禁止 `config/prod.yaml` 修改"）
   - [ ] 若项目继承特定全局规则，`injection.baselineRuleIds` 明确列出
   - [ ] 边界报告清晰表达分工（全局负责什么，项目负责什么）

8. **缺口说明**
   - [ ] 若无在线服务，明确说明"离线导入校验"已通过，哪些验证需要在线
   - [ ] 若某些规则未运行模拟，明确说明原因
   - [ ] 若 `${SESSION_WORKSPACE}` 只在一个工作区路径下验证，说明为什么（如只有开发环境可用）
   - [ ] 不用"已验证"或"已通过"替代实际未做过的验证

## 第三部分：整体质量

9. **完整性**
   - [ ] 新增规则都验证过（至少导入）
   - [ ] 若编辑既有策略，抽查几条未改规则也运行过模拟，确认激活和注入未被意外改写
   - [ ] 项目边界报告完整

10. **可读性与维护性**
    - [ ] narrative 清晰明了，说明规则的目的和应用场景
    - [ ] source 对象指向真实的 AGENTS.md 节点，便于将来查证
    - [ ] 规则 ID 有意义且易于理解（如 `project-ledger-write` 而非 `rule-1`）

**评分**：
- 所有规则通过导入，至少 1-2 条硬规则各有完整正反例模拟，`${SESSION_WORKSPACE}` 展开验证通过，建议规则有质量，与全局基线分工清楚，缺口明确 → 优秀
- 大多规则通过导入，至少 1 条硬规则有完整模拟，缺口清楚说明，项目专属性明显 → 合格
- 导入失败或模拟覆盖极少 → 需改进
- 声称已验证但无实际运行证据，或与全局基线混淆 → 不及格
